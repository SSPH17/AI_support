**Ключевое ограничение**

GitHub, GitLab и другие Git-сервисы не подключаются. Проекты создаются, а README-файлы загружаются вручную через веб-интерфейс.

1. **Общие сведения**

**Наименование:** TeamDocs AI — веб-приложение с RAG-чатботом для работы с README-документацией проектов команды.

**Назначение:** централизованное хранение текстовой документации и интеллектуальный поиск по ней с возможностью получать ответы на естественном языке.

**Целевая аудитория:** разработчики, тестировщики, DevOps-инженеры, технические руководители и другие участники команды.

**Принцип работы**

Пользователь создаёт проект, загружает README, система индексирует файлы; чат ищет релевантные фрагменты и формирует ответ с указанием источников.

2. **Цель и состав проекта**

Разработать единое веб-приложение для размещения README-файлов по отдельным проектам и поиска информации в них с помощью технологии Retrieval-Augmented Generation (RAG).

В состав системы входят:

- каталог проектов с возможностью создания, редактирования и удаления;
- механизм ручной загрузки README и управления версиями документов;
- подсистема обработки Markdown, разбиения на фрагменты и построения эмбеддингов;
- векторная база знаний с привязкой фрагментов к проектам;
- AI-чат с поиском по одному, нескольким или всем доступным проектам;
- история диалогов, просмотр использованных источников и экран состояния индексации.

**Вне объёма MVP:** подключение к GitHub/GitLab, импорт через Git API, автоматическое чтение репозиториев и синхронизация изменений с Git.

# 3. Функциональные требования

### 3.1. Управление проектами

- Создание проекта с обязательным названием и необязательным описанием.
- Просмотр списка проектов, открытие карточки и редактирование атрибутов.
- Привязка к одному проекту произвольного количества поддерживаемых README-файлов.
- Удаление проекта и исключение всех его документов из поискового индекса.
- Логическое разграничение документации разных проектов; при многопользовательской работе — учёт прав доступа.

**Пример:** проект «Authentication Service» с файлами **README.md**, **README\_SETUP.md** и **README\_DEPLOY.md**.

### 3.2. Загрузка и управление документацией

- Загрузка одного или нескольких файлов через кнопку выбора или Drag & Drop.
- Поддержка форматов **.md**, **.markdown**, **.txt** в первой версии.
- Вывод списка файлов, размеров, дат загрузки и статусов обработки.
- Просмотр содержимого файла в веб-приложении.
- Замена файла новой версией с обновлением поискового индекса.
- Удаление документа и связанных с ним поисковых фрагментов.
- Проверка допустимых форматов, ограничений размера, пустых и повторно загруженных файлов.

Статусы: **«Ожидает обработки»**, **«Обрабатывается»**, **«Готов к поиску»**, **«Ошибка обработки»**.

### 3.3. Обработка и индексация README

После загрузки система запускает обработку в фоновом режиме, не блокируя интерфейс пользователя.

- Извлечение текста и структурных элементов Markdown: заголовков, абзацев, списков, таблиц и блоков команд.
- Разбиение на смысловые фрагменты (chunks) с сохранением контекста раздела.
- Формирование эмбеддингов для каждого фрагмента.
- Сохранение текста, векторов и метаданных в БД.
- Привязка фрагмента к проекту, документу, версии и заголовку раздела.
- Исключение устаревших фрагментов после замены или удаления файла.
- Отображение результатов обработки и ошибок в интерфейсе.

Предварительные параметры chunking: **400–800 токенов** с небольшим перекрытием; окончательные значения определяются после тестирования качества поиска.

### 3.4. RAG-чатбот

Веб-чат должен поддерживать вопросы на русском языке с англоязычной технической терминологией, последовательные уточнения и отображение ответа по мере генерации.

| **Режим** | **Описание** |
| --- | --- |
| Один проект | Поиск только по README выбранного проекта. |
| Все проекты | Поиск по документации всех проектов, доступных пользователю. |
| Несколько проектов | Поиск по выбранному набору проектов и сравнение содержащихся в них |

сведений.

- Формирование ответа на основе найденных релевантных фрагментов, а не произвольного предположения модели.
- Сохранение контекста предыдущих сообщений для уточняющих вопросов.
- Поддержка Markdown, списков, таблиц и блоков команд в ответах.
- Предоставление ссылок на фактически использованные документы и разделы.
- Сообщение об отсутствии подтверждающих данных, если в документации нет ответа.
- Проверка разрешённой области поиска при каждом запросе.

### 3.5. Источники и проверяемость ответов

Каждый ответ, основанный на документации, должен содержать блок «Источники» с названием проекта, файла и раздела. Нажатие открывает документ во встроенном просмотрщике с выделением релевантного фрагмента.

**Пример:** «Authentication Service README\_SETUP.md Переменные окружения».

### 3.6. История диалогов

- Создание нового диалога и сохранение сообщений пользователя и ассистента.
- Просмотр списка диалогов и продолжение выбранного диалога.
- Сохранение области поиска и метаданных использованных источников.
- Удаление диалога по запросу пользователя.

4. **Требования к веб-интерфейсу**

Интерфейс должен быть ориентирован на настольные устройства и адаптироваться к меньшим экранам. Основные действия выполняются без перехода на сторонние сервисы.

| **Экран** | **Основные элементы** |
| --- | --- |
| Главная страница | Карточки проектов, поиск по названиям, кнопка создания проекта, переход кобщему AI-чату, последние диалоги. |
| Страница проекта | Название и описание, Drag & Drop, список файлов, статусы обработки, просмотр,замена, удаление, кнопка чата по проекту. |
| AI-чат | Левая панель проектов и истории, центральный диалог, выбор области поиска,правая панель источников. |
| Настройки | Параметры индексации и поиска, выбранная модель, состояние обработки, |

параметры прав доступа.

В интерфейсе необходимо предусмотреть состояния загрузки, пустых списков, ошибок обработки, отсутствия результатов и недоступности языковой модели.

Концептуальные макеты приведены в приложении А. Они описывают компоновку и состав экранов, а не готовый интерактивный дизайн.

### 5.3. Алгоритм загрузки и индексации

- Пользователь выбирает проект и загружает README через веб-интерфейс.
- Backend сохраняет исходный файл и создаёт задачу фоновой обработки.
- Обработчик извлекает Markdown, выделяет фрагменты и связывает их с разделами.
- Сервис эмбеддингов строит векторные представления, которые сохраняются в pgvector.
- После завершения обработки документ получает статус «Готов к поиску».
- При замене или удалении документа старые фрагменты и эмбеддинги исключаются из поиска.

### 5.4. Алгоритм ответа на вопрос

- Пользователь задаёт вопрос и выбирает проекты, по которым разрешён поиск.
- Backend проверяет область доступа и передаёт запрос в RAG-конвейер.
- Выполняются векторный и при необходимости полнотекстовый поиск и ранжирование фрагментов.
- Найденный контекст передаётся в языковую модель вместе с вопросом.
- Чат показывает ответ и ссылки на исходные документы внутри приложения.

# 7. Нефункциональные требования и безопасность

### 7.1. Требования к работе приложения

- Корректная работа в актуальных версиях современных браузеров.
- Адаптивное отображение на настольных и мобильных устройствах.
- Асинхронная обработка файлов без блокировки пользовательского интерфейса.
- Индикация загрузки, прогресса индексации и ошибок.
- Понятное уведомление при сбоях индексации, БД или языковой модели.
- Возможность резервного копирования файлов и базы данных.
- Журналирование системных ошибок и операций обработки без раскрытия чувствительных данных.

### 7.2. Требования к безопасности

- Проверка загрузок: разрешённые расширения, размер, содержимое и безопасное имя файла.
- Запрет исполнения команд, скриптов или инструкций, находящихся внутри README.
- Снижение риска prompt injection: текст документа считается данными, а не системными инструкциями.
- Хранение секретов и ключей языковой модели на серверной стороне.
- Проверка прав доступа к проектам при загрузке документов, просмотре источников и выполнении RAG-запросов.
- Защита передачи данных; политика хранения истории чатов и резервных копий.
- Предварительное согласование возможности передачи содержимого внутренней документации поставщику LLM.

### 7.3. Качество поиска и ответов

Для приёмки необходимо подготовить набор контрольных вопросов с эталонными ответами и точными ссылками на исходные разделы README. Отдельно проверяются вопросы без ответа в документации и попытки получить сведения из недоступных проектов.

Числовые показатели качества, производительности, лимиты загрузки и условия хранения диалогов фиксируются после согласования объёма документации и инфраструктуры.

8. **Основные сценарии использования**

### Сценарий 1. Создание базы знаний

Пользователь открывает приложение, создаёт проект, указывает название и описание, загружает несколько README. После индексации статус файлов меняется на «Готов к поиску».

**Результат: новый проект доступен для поиска в AI-чате.**

### Сценарий 2. Вопрос по конкретному проекту

Пользователь открывает проект «Authentication Service» и спрашивает: «Как запустить сервис локально?» Чат ищет фрагменты только в документах этого проекта.

**Результат: ответ с инструкцией и ссылками на конкретные README.**

### Сценарий 3. Поиск по всем проектам

Пользователь выбирает «Все проекты» и задаёт вопрос: «В каких сервисах используется Redis?»

**Результат: сводный ответ с указанием проектов, где Redis подтверждён документацией.**

### Сценарий 4. Сравнение проектов

Пользователь выбирает два проекта и спрашивает: «Чем различаются инструкции по развёртыванию?»

**Результат: сравнение, опирающееся на README выбранных проектов.**

### Сценарий 5. Замена README

Пользователь загружает обновлённую версию README.md. Система пересоздаёт связанные поисковые фрагменты.

**Результат: новые ответы используют актуальный текст документа.**

### Сценарий 6. Отсутствие ответа

Пользователь спрашивает о параметре, который не описан в загруженной документации.

**Результат: чат сообщает об отсутствии подтверждённых сведений без выдумывания значения.**

9. **Критерии приёмки**

Приложение может быть принято после демонстрации следующих сценариев на тестовых README-файлах:

1. Создание и редактирование проекта через веб-интерфейс.
2. Загрузка нескольких README-файлов в один проект.
3. Автоматическая индексация после загрузки с корректным отображением статуса.
4. Просмотр, замена и удаление загруженного документа.
5. Чат по одному проекту, нескольким выбранным проектам и всем доступным проектам.
6. Ответы с указанием README и релевантных разделов.
7. Открытие источника непосредственно из ответа в приложении.
8. Корректная реакция на отсутствие ответа в документации.
